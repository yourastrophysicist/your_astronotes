# Pseudo-random number generators

a computer cannot produce truly random numbers (it is a deterministic machine). it produces a sequence that *looks* random, generated by a deterministic recurrence with a long period. these are *pseudo-random* numbers (PRNs), and modern PRN generators (PRNGs) are good enough that the distinction never matters for scientific simulation.

## the linear congruential generator (LCG)

the simplest PRNG. starting from a seed $x_0$, generate

$$x_{n+1} = (a x_n + c) \mod m$$

with carefully chosen integer parameters $a, c, m$. the resulting $x_n$ are integers in $[0, m)$, and uniform random reals are obtained by $x_n / m$.

example: glibc's `rand()` used $m = 2^{31}$, $a = 1103515245$, $c = 12345$.

LCGs are simple, fast, and have a period at most $m$. they have known statistical defects (consecutive samples are correlated, low-dimensional projections show structure), and should not be used for serious scientific work.

## the Mersenne Twister

the modern default. period $2^{19937} - 1$, which is overwhelmingly larger than any computation will need (an asymptote of effectively infinite). passes most statistical tests. python's `random` module and numpy's legacy generator (`np.random.RandomState`, the default before numpy 1.17) both use Mersenne Twister.

## numpy's modern API (1.17+)

numpy moved to a `Generator` API with PCG64 as the default, which has better statistical properties than Mersenne Twister:

```python
rng = np.random.default_rng(seed=42)
rng.uniform(0, 1, size=10)
rng.normal(0, 1, size=10)
rng.exponential(scale=1.0, size=10)
```

this is the **recommended modern usage**. the old `np.random.uniform(...)` etc. is still available but uses a global state that is awkward to manage in parallel code.

## seeds and reproducibility

every PRNG has a state. setting the seed initializes the state to a known value. given the same seed, the sequence is byte-identical across runs and across machines (within the same numpy version).

```python
np.random.seed(42)         # legacy API
rng = np.random.default_rng(42)   # new API
```

**always set the seed in production code**. without it:
- **a colleague cannot reproduce my plot** even with my code
- **debugging is harder** — random failures are not random
- **I cannot tell the difference between a real signal and a sampling fluctuation** by re-running

without a seed, numpy uses the system clock + process ID, which is effectively random across runs but unreproducible.

## independent streams for parallel work

if I run $K$ processes in parallel and each draws random numbers, I cannot use the same seed in all of them or they all generate the same sequence. options:

- **different seeds per process**: simple but risks two seeds happening to fall into overlapping states
- **child generators**: `rng.spawn(K)` returns $K$ independent streams from a parent. recommended

```python
parent = np.random.default_rng(42)
children = parent.spawn(K)
# pass children[i] to process i
```

## quality tests for a PRNG

statistical tests applied to a long sequence:

- **uniformity** (chi-square test on the histogram)
- **independence** (autocorrelation should be ~0 at all non-zero lags)
- **higher-dimensional uniformity** (the Marsaglia "diehard" tests; Knuth's tests)

Mersenne Twister and PCG64 pass all standard tests. LCGs fail several.

## true random numbers

for cryptography (or for paranoid simulations), use a hardware source: thermal noise, radioactive decay, atmospheric noise. python's `secrets` module taps the OS's entropy pool. for science, never needed — the deterministic PRN is faster, reproducible, and statistically equivalent.

## period considerations

a PRNG with period $T$ should not be used for simulations requiring more than $\sim T^{1/2}$ samples (the birthday paradox: at that point, the chance of a collision becomes substantial, and what looks like "two independent draws" may secretly be the same number).

- LCG period $\sim 2^{31}$: cannot exceed $\sim 10^4$–$10^5$ samples safely (terrible)
- Mersenne Twister period $\sim 2^{19937}$: practically unlimited
- PCG64 period $\sim 2^{128}$: practically unlimited
